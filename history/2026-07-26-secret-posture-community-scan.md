# Secret-posture community scan — how others handle project/user secrets around untrusted-ish workloads

Date: 2026-07-26. Research question: how do agent-sandbox products, microVM platforms, CI systems, and secret-broker tools handle user/project secrets — and does rip-cage's classify-by-USE hypothesis (Class A wire-bearer / Class B locally-consumed / Class C not-needed) survive contact with community practice?

Method: four parallel research threads (agent sandboxes; microVM + CI; secret brokers; taxonomy prior art + file-masking mechanics), primary sources fetched and verified on 2026-07-26. Claims that could not be verified against a fetched source are marked UNVERIFIED inline.

**Headline:** No mainstream platform even *attempts* to hide a secret from the workload that legitimately uses it — the industry defends with at-rest encryption, best-effort output redaction, and scope+short-lifetime. Workload **non-possession** (msb `--secret`'s property) is rare, but it is not unique: Daytona Secrets and Claude Code's `sandbox.credentials` mask mode are two independent shipping implementations of the exact placeholder+bound-host+wire-substitution design, and CyberArk Secretless Broker / HashiCorp Boundary "credential injection" are its pre-agent-era siblings. The classify-by-use taxonomy is well-precedented (IETF bearer vs proof-of-possession is the same cut) with one refinement the literature insists on: Class B splits in two.

---

## Patterns

### P1 — Plaintext env injection (the universal baseline)

- **Mechanism:** Real secret value set as an environment variable inside the sandbox/VM/job at boot or spawn. Used by Modal (`modal.Secret` → env), E2B (`envs={...}`), Fly.io (`fly secrets` → env at boot from write-only encrypted vault), AWS Lambda (KMS-encrypted config → env at init), Devin, Sculptor (`~/.sculptor/.env`), OpenHands GUI secrets, Cursor "Environment Variables" type, GitHub/GitLab CI variables.
- **Protects / fails:** Protects against secrets baked into images/repos and (with managed storage) gives central rotation. Fails completely against the workload itself: any code in the sandbox reads it; env additionally leaks via `printenv`, `/proc/<pid>/environ`, child-process inheritance, crash dumps. OWASP verbatim: "environment variables are generally accessible to all processes and may be included in logs or system dumps... therefore not recommended unless the other methods are not possible." Fly documents the failure openly: people with deploy access "**can** deploy code that reads secret values and prints them to logs."
- **Autonomy:** Fully preserved — no prompts ever.
- **Taxonomy mapping:** Class-blind. Treats A, B, and C identically (full possession of all three). This is the baseline rip-cage's Class A substitution improves on.
- Citations: https://modal.com/docs/guide/secrets · https://e2b.dev/docs/sandbox/environment-variables · https://fly.io/docs/apps/secrets/ · https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html · https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html · https://docs.devin.ai/product-guides/secrets.md · https://raw.githubusercontent.com/imbue-ai/sculptor/main/docs/help/workspaces.md

### P2 — Output-side redaction / log masking

- **Mechanism:** Plaintext lives in the workload; a runner/SDK scans output channels and replaces exact matches with `***`/placeholder. GitHub Actions runner redaction + `::add-mask::`; GitLab masked variables (`[MASKED]`, ≥8 chars, single line); OpenHands SDK Secret Registry ("masks secret values in command outputs"); Cursor "Runtime Secrets" (redacted from tool results, transcript, commits); 1Password `op run` stdout/stderr masking.
- **Protects / fails:** Protects the LLM context / logs from *accidental* echo — genuinely useful against the "agent cats .env into its own transcript" accident. Known-weak by the vendors' own admission: GitHub — "Because there are multiple ways a secret value can be transformed, automatic redaction is not guaranteed"; base64/URL-encoding pass through; JSON-blob secrets "significantly reduce the probability" of redaction. GitLab — "not a guaranteed way to prevent malicious users from accessing variable values." The 2025 tj-actions incident (below) defeated it trivially with double-base64. Redaction is also post-hoc: an unredacted leak means "delete the log and rotate."
- **Autonomy:** Fully preserved.
- **Taxonomy mapping:** Class-orthogonal *complement*. Works identically for A and B; it protects a different channel (agent-visible output) than substitution (possession). Community practice treats it as a seatbelt, never a boundary.
- Citations: https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions · https://docs.gitlab.com/ci/variables/ · https://docs.openhands.dev/sdk/guides/secrets.md · https://cursor.com/docs/cloud-agent/security · https://developer.1password.com/docs/cli/reference/commands/run/

### P3 — Phase separation: secrets exist only during setup

- **Mechanism:** OpenAI Codex cloud, verbatim: secrets "are only available to setup scripts. For security reasons, secrets are removed before the agent phase starts." Cursor "Build Secrets" are the same idea scoped to `docker build --mount=type=secret` — never in the runtime image.
- **Protects / fails:** Fully protects against agent-phase read *and* prompt-injection exfil (nothing to steal at agent time). Fails for any task where the agent itself needs the credential mid-run — authenticated API testing, deploys, DB work all become impossible. Security by making the work impossible.
- **Autonomy:** Preserved in the letter (no prompts) but violated in spirit for credential-needing tasks — the agent hits a wall and must stop or ask.
- **Taxonomy mapping:** This is Class C generalized to *all* secrets — "treat everything as not-needed-by-caged-work." Valid only when true; rip-cage's Class A exists precisely for the tasks Codex's model forfeits.
- Citations: https://developers.openai.com/codex/cloud/environments · https://cursor.com/docs/cloud-agent/security

### P4 — Placeholder + wire substitution bound to a host allowlist (the msb `--secret` family)

- **Mechanism:** Workload holds an opaque placeholder; an egress proxy substitutes the real value on the wire only toward bound hosts. **Daytona Secrets** (shipping): `dtn_secret_<random>` placeholder in env; HTTPS-header-only substitution when destination matches the secret's `hosts` allowlist; placeholder forwarded unchanged elsewhere; plus **response scrubbing** — real value appearing in a response is rewritten back to the placeholder before reaching the sandbox. **Claude Code `sandbox.credentials` mask mode** (v2.1.199+): per-session sentinel; proxy replaces it toward `injectHosts`; requires `tlsTerminate`; **fails closed** without it; mask entries honored only from user/managed settings, never repo-local (anti-prompt-injection). **CyberArk Secretless Broker**: same property via protocol-aware connectors — replaces the *authentication handshake* for Postgres, MySQL, SSH, HTTP Basic, and even computes AWS SigV4 signatures on the client's behalf. **HashiCorp Boundary "credential injection"** names the concept: creds "passed on to a worker for authentication to a remote machine... the user never sees the credential" (vs mere "credential brokering" where the user receives and types them).
- **Protects / fails:** Removes possession: memory dumps, `cat .env`, transcript leaks, and exfil to non-bound hosts all yield only the placeholder. Documented failure surfaces (all vendor-admitted): plain HTTP never substituted (Daytona); request **bodies and URL query params** not substituted — "If a service only accepts credentials in the body or query string, secrets cannot authenticate to it" (Daytona); **any client-side transformation breaks matching** — Basic-Auth base64 encoding defeats it (Daytona's workaround: store the pre-encoded value); **mTLS upstreams and certificate-pinning clients cannot be TLS-intercepted at all** (srt: "only the in-sandbox client holds the client certificate, so the proxy cannot re-originate the connection" — `excludeDomains` tunnels them opaquely, losing substitution); non-HTTP protocols need a per-protocol connector (Secretless proves it's possible but its connectors are beta-for-years — real maintenance cost). Residual risk shared by the whole family: **capability survives possession-removal** — a prompt-injected agent can still *drive* the proxy toward the bound host (confused deputy). Community answer: pair with short-lived/scoped upstream creds (P6). And the bound host itself can *reflect* the plaintext back in a response — Daytona's response scrubbing exists for exactly this; rip-cage/msb should check whether it has an equivalent.
- **Autonomy:** Fully preserved — no prompts; Daytona even rotates secrets on a live sandbox (~15s propagation).
- **Taxonomy mapping:** This *is* Class A, independently converged on three times (Daytona, Claude Code, msb) plus the pre-agent sibling (Secretless/Boundary). Secretless's DB-protocol connectors show the A/B border is a *protocol-support* line, not a physics line — see Taxonomy check.
- Citations: https://www.daytona.io/docs/en/secrets.md · https://docs.claude.com/en/docs/claude-code/sandboxing.md · https://raw.githubusercontent.com/anthropic-experimental/sandbox-runtime/main/README.md · https://raw.githubusercontent.com/cyberark/secretless-broker/main/README.md · https://developer.hashicorp.com/boundary/docs/concepts/credential-management

### P5 — File-path masking / denyRead inside the workspace (the Class C mechanics)

- **Mechanism:** Hide the secret file from the mounted tree. Canonical prior art: OCI runtime-spec `maskedPaths` — runc "bind mounts /dev/null over the top" of files and mounts "read-only tmpfs over the top" of directories (used by every container runtime for /proc/kcore etc.). srt/Claude Code sandboxing: filesystem `denyRead` rules (README examples deny `~/.ssh` and `.env`). Docker: bind-mount shadowing ("pre-existing files are obscured by the mount"); tmpfs mounts are **directories only** — a file mask needs the /dev/null-bind trick. Overlayfs whiteouts can present a filtered view but writes land in the upper layer (breaks live host↔guest sync — poor fit for rip-cage's primary workspace mount).
- **Protects / fails:** Removes the private-data leg entirely for that file — stronger than redaction, equal to non-possession, but only valid when the caged work genuinely doesn't need the file. Gotchas: masks don't hide path *existence* (stat shows a char device); a bind-mounted single file tracks the inode, so rename-replace edits desync it (moby#15793); a nonexistent bind source silently becomes a directory; **git hazard** — /dev/null over a *tracked* file reads as a typechange, and an agent running `git add -A` can commit the destroyed file (mitigate: mask only untracked/gitignored files, or pair with `git update-index --skip-worktree` in init); agents can regenerate the secret via its generator (`terraform output`, re-run direnv) — masking can't address that. Placement matters: guest-side masks are removable by guest root; **host-side overmounts served through virtiofs are not** (mask lives in the host mount table) — virtiofsd traverses and exposes host submounts (`--announce-submounts` default on). **UNVERIFIED, load-bearing:** whether libkrun's in-process virtio-fs honors host overmounts inside the share, and whether overmounts made while the sandbox runs become visible — settleable with a 5-minute probe (`mount --bind /dev/null <ws>/.env` on host, stat in guest). Also note libkrun's README warning: its virtio-fs "does not provide any protection against the guest attempting to access other directories in the same filesystem" without a host-side mount-isolation mechanism — naive "relocate to a sibling dir" may not actually be out of reach unless msb adds isolation (verify against msb).
- **Autonomy:** Fully preserved; failure mode is *silent breakage* — a local process that legitimately needed the masked file gets empty bytes and errors confusingly (misclassifying B as C costs autonomy downstream). Argues for a legible "masked by rip-cage" breadcrumb where consumers tolerate it.
- **Taxonomy mapping:** Directly implements Class C; `maskedPaths` is battle-tested production precedent including the file-vs-directory mechanism split.
- Citations: https://raw.githubusercontent.com/opencontainers/runtime-spec/main/config-linux.md · https://raw.githubusercontent.com/opencontainers/runc/main/libcontainer/rootfs_linux.go (`maskPaths`) · https://raw.githubusercontent.com/anthropic-experimental/sandbox-runtime/main/README.md · https://docs.docker.com/engine/storage/bind-mounts/ · https://docs.docker.com/engine/storage/tmpfs.md · https://github.com/moby/moby/issues/15793 · https://docs.kernel.org/filesystems/overlayfs.html · https://gitlab.com/virtio-fs/virtiofsd/-/raw/main/README.md · https://raw.githubusercontent.com/containers/libkrun/main/README.md

### P6 — Short-lived / dynamic issuance (theft-tolerance, not theft-prevention)

- **Mechanism:** Don't hide the credential — make possession low-value. Vault dynamic secrets: per-consumer DB credentials generated on demand (default TTL 1h), auto-revoked — the flagship example is **PostgreSQL passwords**. GitHub Actions OIDC: "request a short-lived access token directly from the cloud provider... only valid for a single job, then automatically expires" — the documented replacement for long-lived cloud secrets in CI. AWS STS via instance roles. LiteLLM-style gateway virtual keys: client holds a revocable, budget-capped proxy key; the gateway holds real provider keys.
- **Protects / fails:** Bounds blast radius of any leak to TTL × scope; survives the memory-dump attack that defeats P2 (the stolen thing expires). Doesn't stop in-lifetime misuse; requires the target service to support ephemeral issuance ("services that do not support creating temporal roles or credentials" remain static — OWASP).
- **Autonomy:** Fully preserved given machine identity (AppRole/K8s SA/OIDC — no prompts).
- **Taxonomy mapping:** **This is the community's main answer to Class B** — and it's why the literature splits B (see Taxonomy check). It also composes with Class A: a leaked-or-misused substituted credential should itself be short-lived and per-cage.
- Citations: https://developer.hashicorp.com/vault/docs/secrets/databases · https://developer.hashicorp.com/vault/tutorials/get-started/understand-static-dynamic-secrets · https://docs.github.com/en/actions/concepts/security/openid-connect · https://docs.litellm.ai/docs/proxy/virtual_keys · https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html

### P7 — Sidecar/file delivery to tmpfs (secret-delivery, not non-possession)

- **Mechanism:** A trusted agent renders secrets to files the app reads. Vault Agent Injector: mutating webhook adds init+sidecar containers rendering to a shared memory volume at `/vault/secrets`; K8s secret volumes: kubelet "stores a copy of the data into a tmpfs so that the confidential data is not written to durable storage"; GitLab file-type variables ("prevent commands such as `env` or `printenv` from printing secret variables"); Cloud Run secret volumes fetch live from Secret Manager (rotation without restart).
- **Protects / fails:** Files beat env vars (no /proc/environ, no child inheritance, off durable storage); rotation transparent. The workload still fully possesses the secret at use time; K8s docs are candid that etcd storage is unencrypted by default and node-privileged containers see everything.
- **Autonomy:** Fully preserved.
- **Taxonomy mapping:** Class-blind delivery; the community's *best-practice baseline* for Class B secrets when dynamic issuance (P6) isn't available. For rip-cage: if a Class B secret must ride into the cage, a tmpfs-delivered file is strictly better than the bind-mounted `.env`.
- Citations: https://developer.hashicorp.com/vault/docs/deploy/kubernetes/injector · https://kubernetes.io/docs/concepts/configuration/secret/ · https://docs.gitlab.com/ci/variables/ · https://cloud.google.com/run/docs/configuring/services/secrets

### P8 — Ambient identity via metadata service (no secret material in config)

- **Mechanism:** Workload queries a link-local endpoint for short-lived role credentials. AWS IMDS (v2: session PUT + token, hop-limit 1, rejects `X-Forwarded-For` — anti-SSRF); Firecracker MMDS is the same primitive for microVMs: host writes/patches a JSON store via the API socket **while the VM runs**, guest polls; "not persisted across snapshots"; the docs' own appendix shows host-driven credential rotation.
- **Protects / fails:** Nothing to leak from config/repo/env; theft bounded by STS lifetime; host retains unilateral rotation. Fails: ambient authority is per-*host* — **any process in the guest can hit the endpoint**, which is exactly rip-cage's threat (a prompt-injected agent is a local process). This failure is *why* msb `--secret` binds substitution to a destination host rather than granting ambient access.
- **Autonomy:** Fully preserved — the canonical zero-prompt pattern.
- **Taxonomy mapping:** Alternative frame to Class A for cloud creds; loses to substitution on the local-process axis. MMDS is interesting to rip-cage as *mechanism* (host-controlled live-mutable value store into a running libkrun-family VM) rather than as posture.
- Citations: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html · https://github.com/firecracker-microvm/firecracker/blob/main/docs/mmds/mmds-user-guide.md

### P9 — Encrypted-at-rest / spawn-time resolution (protects a different window)

- **Mechanism:** sops/age: values encrypted in git via envelope encryption (per-file data key wrapped by KMS/age/PGP), decrypted at use time; CNCF Sandbox. 1Password `op run`: `op://` references in `.env` resolved at process spawn into the child's env only — nothing plaintext on disk. direnv: `.envrc` evaluated on cd, exports into the shell env (inherited by *every* descendant — strictly weaker than `op run`).
- **Protects / fails:** Protects the at-rest/in-git window only; at use time the consumer holds full plaintext (1Password's own docs: "You should assume that processes on your computer can access the environment of other processes run by the same user"). For rip-cage: an agent in the cage that can run `sops -d` or `op run` has the plaintext — these tools relocate the secret *boundary* to the KMS/vault credential, which then needs its own classification.
- **Autonomy:** sops-with-KMS and `op` service accounts: prompt-free. `op` desktop-app integration defers to biometric unlock (UNVERIFIED for today's fetch, prior knowledge) — breaks walk-away autonomy. Passphrase-protected PGP: interactive.
- **Taxonomy mapping:** Orthogonal to A/B/C (at-rest axis); relevant mainly because encrypted-at-rest secret files in a workspace are *safe to ride into the cage* as long as the decrypt credential doesn't.
- Citations: https://raw.githubusercontent.com/getsops/sops/main/README.rst · https://developer.1password.com/docs/cli/secrets-environment-variables/ · https://raw.githubusercontent.com/direnv/direnv/master/man/direnv-stdlib.1.md

### P10 — Scoping and admission control (access control, not concealment)

- **Mechanism:** GitLab protected variables (only pipelines on protected branches see deploy creds); GitHub fork-PR policy ("secrets are not passed to the runner when a workflow is triggered from a forked repository", except GITHUB_TOKEN) + environment required-reviewers; Devin's "dedicated account for Devin" guidance; Claude Code honoring `mask` config only from user/managed settings, never repo-local (a hostile checked-out repo cannot self-authorize sending a credential anywhere).
- **Protects / fails:** Contains *who/which context* gets the secret; does nothing once the authorized context is compromised (GitLab verbatim: "malicious code can compromise both masked and protected variables"). The `pull_request_target` pwn-request class is what happens when the admission boundary is misdrawn.
- **Autonomy:** Preserved (pre-run admission gates, not mid-run prompts).
- **Taxonomy mapping:** Orthogonal but load-bearing for rip-cage: the config-authority rule (Claude Code's settings-provenance rule ≈ rip-cage's ro-mounted `.rip-cage.yaml`) is convergent evolution — *who may bind a secret to a host* must be outside the cage's write authority.
- Citations: https://docs.gitlab.com/ci/variables/ · https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions · https://docs.claude.com/en/docs/claude-code/sandboxing.md · https://docs.devin.ai/product-guides/secrets.md

## Failure modes observed in the wild

1. **Memory-dump exfiltration defeats masking and vaults alike — tj-actions/changed-files (CVE-2025-30066, March 2025).** A compromised action dumped the CI runner's `Runner.Worker` process memory (which holds all job secrets) and printed them to public logs as **double-encoded base64**, sailing past exact-match redaction. AWS keys, GitHub PATs, npm tokens, private RSA keys leaked from public repos; CISA KEV-listed. The cleanest demonstration that *any secret present in the job's memory/env is exfiltratable by anything running in the job* — the exact attack class placeholder-substitution defeats. (https://www.wiz.io/blog/github-action-tj-actions-changed-files-supply-chain-attack-cve-2025-30066 · https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-github-action-cve-2025-30066)
2. **Exact-match redaction is transformation-fragile by design** — vendor-documented (GitHub: base64/URL-encoding/JSON blobs defeat it; GitLab: shell-escaping defeats it; `CI_DEBUG_SERVICES` can reveal values). Never a boundary.
3. **Transformation also breaks wire-substitution** — Daytona documents that Basic-Auth helpers base64-encoding the credential produce a non-matching header (workaround: store the pre-encoded value); body/query-param credentials can't authenticate at all. Class A membership requires *verbatim* wire appearance — this is the operational test.
4. **mTLS and certificate pinning are TLS-interception dead zones** (srt): the proxy cannot re-originate a connection whose client cert lives only in the sandbox; pinning clients reject the interposed CA. `excludeDomains`-style escape hatches tunnel opaquely — substitution and inspection both lost for those hosts.
5. **Capability outlives possession (confused deputy).** Every non-possession broker (Secretless, Boundary, Daytona, msb) leaves the compromised workload able to *use* the open channel toward the bound host. Community mitigation: short-lived/scoped upstream creds (P6) so even capability is time-boxed.
6. **The bound host reflects the plaintext back.** A response from the legitimate host can contain the real credential (echo endpoints, error messages, account pages) — Daytona ships response scrubbing for this. Check msb for an equivalent; without it, Class A non-possession has a readback hole.
7. **Allowed egress hosts are exfil channels.** srt: "allowing github.com lets a process push to any repository"; Codex docs give a worked prompt-injection exfil example and recommend domain allowlists + GET/HEAD/OPTIONS-only modes; domain fronting flagged. Placeholder substitution caps what *secrets* leak, not what *data* leaks.
8. **Ambient authority is readable by every local process** — IMDSv1/SSRF class (Capital One 2019, attribution UNVERIFIED today); IMDSv2's hardening closes the remote hole, not the local one. Any "just query the metadata endpoint" design hands the credential to a prompt-injected agent.
9. **Env vars leak sideways** — `/proc/<pid>/environ`, child inheritance, `ps` for command-line args, crash dumps (OWASP; GitHub docs on `ps`). Files-on-tmpfs is the consistently recommended stronger delivery.
10. **File-masking sharp edges:** single-file bind mounts track inodes and desync on rename-replace saves (moby#15793); nonexistent bind sources silently become directories; masking a *tracked* file makes `git add -A` commit the destruction (typechange to char device); agents can regenerate masked secrets from generators; K8s subPath symlink race (CVE-2017-1002101) shows host-side path resolution over an agent-writable tree is a race surface.
11. **Mid-run credential prompts exist in the wild and are the anti-pattern** — Devin documents asking the user for credentials mid-conversation (its TOTP-seed feature exists precisely to stop 2FA interrupting runs); 1Password desktop-integration defers to biometric unlock. Both violate rip-cage's walk-away requirement; both are avoidable (pre-provisioning, service accounts).
12. **Unrestricted-by-default binding:** a Daytona secret with no `hosts` list is substituted toward *any* host — the allowlist is opt-in per secret. Default-bind-to-declared-host (msb's model) is the safer default.

## Taxonomy check — does classify-by-use survive?

**Verdict: yes, with one mandatory refinement (split Class B) and two frame supplements.**

**Supporting evidence:**
- **IETF made the same cut at protocol level.** RFC 6750 bearer tokens ("any party in possession can use") vs RFC 9449 DPoP / RFC 8705 mTLS-bound tokens (wire artifact worthless without a local private key). Bearer ↔ Class A (substitutable on the wire); proof-of-possession key ↔ Class B (local process needs the real bytes — un-proxyable *by construction*). RFC 9449 §11.4 ("Untrusted Code in the Client Context") is the caged-agent threat framing. (https://www.rfc-editor.org/rfc/rfc6750.txt · https://www.rfc-editor.org/rfc/rfc9449.txt · https://www.rfc-editor.org/rfc/rfc8705.txt)
- **NIST SP 800-57 Part 1 §5.1.1 canonizes classify-by-use** ("classifies the different types of keys... according to their uses" — ~21 types, protections derived from use). All NIST types are Class B; Class A is the API-key-economy gap the IETF work covers. (https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf p.30)
- **TruffleHog's verification machinery operationalizes Class A**: "classifies over 800 secret types" and "can log in to confirm if that secret is live" — verifiable ≡ known-remote-endpoint-accepts-these-bytes ≡ wire-bearer. Its detector list is a ready-made machine-readable Class A enumeration *with the bound hosts encoded* — a candidate classification oracle for rip-cage. (https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/README.md)
- **Class A shipped three times independently** (Daytona, Claude Code mask mode, msb `--secret`) with Boundary supplying the canonical vocabulary ("credential injection... the user never sees the credential") and Secretless the pre-agent implementation.
- **Class C has direct production prior art**: OCI `maskedPaths`/runc is exactly "mask files in a mounted tree," down to the file-vs-directory mechanism split; srt `denyRead` of `.env` is the same posture in the agent world; Codex setup-only secrets is Class C applied to everything.

**Contradicting / refining evidence:**
- **Class B is two classes, and the community solves the bigger half.** OWASP and Vault split static vs dynamic: **B1 — locally-consumed but dynamically issuable** (DB passwords are Vault's *flagship dynamic-secret example*, not an unsolvable case): mitigate with short-lived scoped per-cage issuance, fully autonomy-preserving. **B2 — structurally static key material** (signing keys, storage-encryption keys, TLS/mTLS private keys): the genuinely irreducible possession core. "Substitution structurally impossible" is true of B2; for B1 the honest statement is "substitution unnecessary — make possession cheap instead."
- **The A/B border is protocol-support, not physics.** Secretless Broker substitutes *inside* Postgres/MySQL auth handshakes and SSH, and even computes AWS SigV4 signatures for the client — so a remote-DB password is Class A *given a protocol-aware connector*. The border rip-cage should draw: **A = verbatim in an HTTPS header toward a known host (msb-supported today); A-extended = protocol-connector territory (possible, high per-protocol maintenance cost — Secretless's connectors are beta-for-years); B2 = never.** Truly *local* consumption (a Postgres server in the cage reading its own password, a signing operation) stays B regardless.
- **The agent-security community uses a complementary frame, not a competing one.** No published source found using an A/B/C-by-use taxonomy; the dominant frame is Simon Willison's lethal trifecta (private data + untrusted content + external communication). It maps cleanly: Class C removes the private-data leg per-file; Class A substitution is *stronger than removal* (even a fully injected agent that reads the placeholder exfiltrates nothing real); but the trifecta adds what the taxonomy misses — the egress allowlist hosts themselves remain a data-exfil channel, and possession-removal doesn't remove capability. (https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **CI's lifetime axis is a supplement A/B/C lacks.** The industry's deepest lesson (OIDC, dynamic secrets, STS) is that *every* class benefits from short lifetime + narrow scope — classify-by-use says where the secret may exist; classify-by-lifetime says how much a failure costs. The strongest posture composes both: Class A substitution of a credential that is *also* per-cage and short-lived.

**Suggested refined taxonomy:** A (wire-bearer, HTTPS-header verbatim → substitute; TruffleHog-verifiable is the membership test) · A-ext (wire-bearer over non-HTTP protocols → substitutable in principle, per-protocol connector cost) · B1 (locally-consumed, dynamically issuable → short-lived per-cage issuance) · B2 (structurally static key material → keep out of the cage, or accept possession knowingly, tmpfs-delivered not workspace-resident) · C (not needed → host-side mask/relocate, maskedPaths-style).

## Autonomy-preserving shortlist

Patterns fully compatible with unattended agent runs (no interactive prompts mid-run), ordered by relevance to rip-cage:

1. **Placeholder + bound-host wire substitution (P4)** — Class A. Shipping precedent: Daytona, Claude Code mask mode. Adopt Daytona's two extras: *response scrubbing* (closes the readback hole) and treat *no-host-binding* as invalid rather than unrestricted. Keep Claude Code's config-provenance rule (bindings only from outside-the-cage config — rip-cage already has this via ro `.rip-cage.yaml`).
2. **Host-side file masking through virtiofs (P5)** — Class C. /dev/null-bind for files, ro-tmpfs for directories, per runc `maskPaths`; host-side placement makes it guest-tamper-proof. **Gate on the one unverified fact: probe whether msb/libkrun virtiofs exposes host overmounts to the guest (5-minute test) before designing on it.** Mask only untracked files or pair with `skip-worktree`; leave a legible breadcrumb.
3. **Short-lived / per-cage issuance (P6)** — the B1 answer and the A complement. Vault dynamic secrets, OIDC-style exchange, gateway virtual keys (LiteLLM pattern for LLM API keys specifically). No prompts given machine identity.
4. **tmpfs file delivery over env vars (P7)** — the fallback when a Class B secret must enter the cage: strictly better than riding in the bind-mounted workspace tree.
5. **Output-side redaction (P2)** — cheap seatbelt against accidental transcript echo; never load-bearing (transformation-fragile). OpenHands SDK and `op run` show it composes with everything else.
6. **Setup-phase-only secrets (P3)** — valid for genuinely build-time-only credentials (Cursor Build Secrets model); as a global posture it forfeits credential-needing agent tasks.
7. **Host-controlled live-mutable metadata (P8, MMDS-style)** — not as ambient authority (fails the local-process test) but as *mechanism*: host-side rotation into a running microVM without restart is proven in the Firecracker family.

Explicitly *failing* the autonomy bar: Devin-style mid-run credential prompts, 1Password desktop-app biometric unlock, Teleport/Boundary SSO/MFA session entry (their machine-identity variants — Machine ID/tbot — would pass but were not verified this scan).

# What designs stop host git (and host IDEs) from executing commands from repo config/hooks that a caged agent wrote, at workbench scale (~/code rw, 88+ repos), and what is the libkrun/msb device ceiling?

2026-11-09 · deep (4 angles merged: libkrun ceiling, msb features, git controls, other sandboxes) · caller: brain:rip-cage design brainstorm (human + brain) · feeds: choosing rip-cage's replacement for ADR-002 D11 (per-repo read-only virtiofs host mounts over .git/config, .git/info, .git/hooks, commondir, plus a rw self-pin of .git). No recommendation is made here; breadth and honest tradeoffs only.

**ADR-002 D11 is FIRM.** Any candidate below that changes it is the human's call, not an agent's.

## Answer
The `RegisterFsDevice(IrqsExhausted)` failure is raised by libkrun's device manager when its IRQ range runs out [2][3]; msb pins msb_krun 0.1.45 [1] and adds its virtio-fs devices through `builder.fs(...)` [4]; the probe log from the 88-repo run printed this error [48]. In git, protected configuration is the system, global and command scopes, some options are respected only there, and `safe.directory`, the ownership guard, compares the owner's uid with the effective uid [18][19][20][21]. Environment-variable config (`GIT_CONFIG_COUNT` and friends) overrides values in configuration files and is itself overridden by `git -c` [21]. Claude Code's sandbox and sandbox-runtime deny writes to `.git` hooks and config inside the writable tree [37][38]; Codex protects the top-level `.git` name [39]; Pillar's write-up says a Cursor sandbox deny rule matched a string, not Git [42]; Claude Code made `.git` an invalid worktree name [43]; Docker Sandboxes clone mode mounts the repo read-only and works on a private clone inside the VM [40]; Codespaces run in a Docker container on a VM [45]. In a probe, 400 in-guest bind covers over one share applied, a non-root `umount` was refused, guest root could unmount a cover and write through, an absent file could still be created, and a write through a tmpfs-upper overlay left the host file unchanged [49].

## Device ceiling
- **Source of the limit.** The device manager returns `IrqsExhausted` when the next IRQ is past the range end; the fs attach path wraps it as `RegisterFsDevice` [2][3]. The probe log from the 88-repo ~/code run shows the same error text [48]. That run's dry-run argv passed 393 `-v` mounts on the msb command line, before the config file's own mounts [51]; the 415-device / 382-git-cover totals are the caller's bead comment (rip-cage-rsh9.14, 2026-11-09).
- **x86_64 KVM, in-kernel IOAPIC:** IRQ_BASE 5 to IRQ_MAX 15, about 11 devices [5][6].
- **x86_64 KVM, split irqchip** (msb enables it on Linux x86_64 only): range 5..119, about 115 devices, minus the devices msb itself registers (root, runtime share, console, vsock, net; exact count not measured, roughly 5-8) [4][5][6][8].
- **aarch64 (macOS/HVF host):** upper bound IRQ_MAX 223 in the msb fork; the angle states the range as 32..223, about 192 devices, but the captured quote shows only the max [7].
- **One device per mount:** msb adds a virtio-fs device through `builder.fs(...)` [4]; that one is added per volume mount is read from the loop around that line, which the quote does not include (reasoning). At the observed ~4-5 mounts per repo (reasoning: 382 covers / 88 repos is about 4.3), that is a ceiling near 20-25 repos on Linux x86_64 and near 40 on aarch64, before the msb-own-device deduction (reasoning).
- **Can it be raised?** It is a compile-time constant in the arch crate; split irqchip is a runtime API but already on for Linux x86_64 and x86_64-only; no msb option that changes the range was found [5][6][8]. Raising needs a patch/upgrade of the msb libkrun fork. Upstream libkrun main shows a shared `IrqAllocator` that also serves PCI INTx, but whether PCI virtio-fs is reachable via msb_krun 0.1.45 or msb was not confirmed [9][10]. One virtiofs share costs one device regardless of how many repos sit in it [4].

## Findings

### Device ceiling (libkrun, msb)
- Error site: the device manager errors once the IRQ range is exhausted and the fs attach path maps it to `RegisterFsDevice` — AUTHORITY (source)
  > "if self.irq > self.last_irq { return Err(Error::IrqsExhausted); }" [2]
  > "attach_mmio_device(vmm, id, intc.clone(), fs).map_err(RegisterFsDevice)?;" [3]
- The run that failed prints this error — AUTHORITY (local probe log)
  > "build_vm: VM enter: build error: start: build_microvm: RegisterFsDevice(IrqsExhausted)" [48]
- The manager is built from an `(IRQ_BASE, irq_max)` pair — AUTHORITY
  > "let mut mmio_device_manager = MMIODeviceManager::new( &mut (arch::MMIO_MEM_START.clone()), (arch::IRQ_BASE, irq_max), );" [5]
- x86_64 constants and the KVM in-kernel IOAPIC pin count — AUTHORITY
  > "pub const IRQ_BASE: u32 = 5;" [6]
  > "pub const IRQ_MAX: u32 = 15;" [6]
  > "pub const KVM_IOAPIC_NUM_PINS: usize = 24;" [6]
- Split irqchip sets x86_64's max to `IOAPIC_NUM_PINS - 1`; the userspace IOAPIC has 120 entries, so the max is 119 by arithmetic — AUTHORITY
  > "pub const IRQ_MAX_SPLIT: u32 = IOAPIC_NUM_PINS as u32 - 1;" [6]
  > "pub const IOAPIC_NUM_PINS: usize = 120;" [6]
  > "if split_irqchip { arch::IRQ_MAX_SPLIT } else { arch::IRQ_MAX }" [5]
  > "This lifts the virtio MMIO IRQ count from 11" [5]
  > "(IRQ_BASE..=IRQ_MAX) to NUM_PINS-IRQ_BASE, enough for a guest with several virtiofs mounts." [5]
- Split irqchip is a runtime API, x86_64 only; msb enables it on Linux x86_64 only — AUTHORITY
  > "if enable && !cfg!(target_arch = "x86_64") { return -libc::EINVAL; }" [8]
  > "#[cfg(all(target_os = "linux", target_arch = "x86_64"))] { m.split_irqchip(true) }" [4]
- msb registers a virtio-fs device through `builder.fs(...)` with a custom backend (that this runs once per mount is read from the surrounding loop, not quoted) — AUTHORITY
  > "builder = builder.fs(move |fs| fs.tag(&tag).custom(Box::new(backend)));" [4]
- msb pins the fork at 0.1.45 — AUTHORITY
  > `msb_krun = "=0.1.45"` [1]
- aarch64 fork range upper bound — AUTHORITY
  > "pub const IRQ_MAX: u32 = 223;" [7]
- Upstream libkrun main: a smaller x86_64 IRQ_MAX, and a device-manager source that says MMIO and PCI INTx managers draw IRQs from one allocator — AUTHORITY
  > "pub const IRQ_MAX: u32 = 23;" [9]
  > "let irq = range.next.ok_or(IrqsExhausted)?;" [10]
  > "Every device manager that needs an IRQ (MMIO, PCI INTx) must draw it from" [10]
  > "the same allocator, otherwise two devices end up sharing a line." [10]

### Git-side controls
- safe.directory is the ownership guard; the ownership check compares `st_uid` with the effective uid — AUTHORITY (docs + source)

  > "if (!git_env_bool("GIT_TEST_ASSUME_DIFFERENT_OWNER", 0) && (!gitfile || is_path_owned_by_current_user(gitfile, report)) && (!worktree || is_path_owned_by_current_user(worktree, report)) && (!gitdir || is_path_owned_by_current_user(gitdir, report))) return 1;" [19]

## Dissent and counter-arguments
- Where a denylist is git-aware: sandbox-runtime blocks `.git/hooks` when `.git` is a directory and denies a `.git` file outright; this is the working-denylist side of the argument.
  > "if (dotGit === DotGitKind.Directory) { // Git hooks always blocked for security denyPaths.push(path.resolve(cwd, '.git/hooks'))" [38]
  > "if (dotGit === DotGitKind.File) { denyPaths.push(dotGitPath) }" [38]
- Against a host git wrapper (candidate 6): the quoted hook docs show a per-name disable for `hook.<name>.command`.
  > "Set to `false` to disable the hook without removing its configuration." [33]
- Git treats system, global and command scopes as controlled by the user or a trusted administrator, which puts a repo-config defence outside git settings.
  > "Git treats these scopes as if they are controlled by the user or a trusted administrator." [21]
- Searched, none found: a git "ignore repo config" option. Queries: `ignore_repo`, GIT_CONFIG_NOGLOBAL, NO_REPO_CONFIG and "ignore.*repo.*config" in config.c, environment.c, setup.c, Documentation/git.adoc; only internal uses. No web search was run, so a mailing-list proposal could exist unseen.
- Upstream libkrun main: its irq.rs says MMIO and PCI INTx device managers draw IRQs from one allocator, which could in principle matter for the per-device limit; whether PCI virtio-fs is reachable via msb_krun 0.1.45 or exposed by msb was not confirmed (grep for `pci` in the fork's builder found none; no msb transport option found).
  > "Every device manager that needs an IRQ (MMIO, PCI INTx) must draw it from" [10]
- Clone mode (candidate 5) protects the host repo, not secrets in it.
  > "Clone mode protects your host repository from modification, not from inspection." [40]
- Searched, none found: msb host-dir overlay or per-path ro. Queries: volumes.mdx for filter/exclude/ignore/subpath/hide, and "overlay" repo-wide.

# How do other agent sandboxes handle the host's git repositories and credentials: bind-mount, clone, or separate volume; .git protection; push credentials and .env; many repos?

2026-11-11 · depth deep (3 angles) · caller worker:rip-cage-rsh9.14 · decision: rip-cage-rsh9.14 clone-volume design and the nested-repo hide rule

## Answer
- Clone, not mount: Codex checks out the repo in a container, Cursor cloud agents clone it, and Jules clones it in a VM [1][5][6]; Docker Sandboxes can clone repositories inside the sandbox with no host workspace attached [14]. It diverges from the local mainstream: Claude Code's devcontainer bind-mounts the host workspace folder at /workspace, Docker's direct mount is read-write, and `sbx run` shares the current directory by default [9][13]. Cursor before 2.5 let a malicious (e.g. prompt-injected) agent inside the sandbox rewrite the insufficiently protected .git config [23], and the GitSpawn write-up says a git clone from a stranger is safer than a .zip from a colleague [24].
- Nested-repo hide: Claude Code's docs scope the `.git` hooks and config entry to "In your working directory only" [10]; no precedent for hiding nested repos turned up in the sources read (see Unverified), so treat it as rip-cage's own rule.
- Read-only covers on a mounted repo: inside the directories sandboxed commands can write to, Claude Code's built-in sandbox still denies writes to the files Claude Code loads configuration and code from [10]. Cursor before 2.5's agent could rewrite .git config, and if it could write Git hooks, code ran outside the sandbox [23]; microsandbox has per-mount `readonly` / `ro` for when the guest should not write to the mount [12]. Claude Code says not to rely on protected paths when `allowNestedUserNamespaces` is true on Linux or WSL2, so treat covers as best-effort [10].
- Injected scoped token: several sources keep real credentials outside the sandbox. Anthropic's web sandbox never holds git credentials inside [25], Cowork keeps them in the host keychain and gives the VM a per-session scoped-down token [26], Docker sbx's host-side proxy injects authentication headers [13], nanoclaw's OneCLI proxy injects real credentials in place of a placeholder key [15], and microsandbox lets a workload call an API with a credential it never holds [11]. It diverges from Copilot, whose cloud agent can push only to a single branch and cannot directly run git push or other Git commands [4], and from Codex, which removes secrets before the agent phase starts [1]. Limits: microsandbox substitution needs TLS inspection for that host [11], and Anthropic reports its custom allowlist proxy was the piece that failed [26].
- Many repos at once: for simultaneous tasks Docker has the agent create a separate worktree or clone for each task inside the sandbox [14]. Copilot sessions can span repositories in one organization [3], and Cursor needs read-write privileges to the repo and any dependent repos or submodules [5].

  > `"workspaceMount": "source=${localWorkspaceFolder},target=/workspace,type=bind,consistency=delegated",` [9]
- Claude Code built-in sandbox: inside directories sandboxed commands can write to, it still denies writes to files Claude Code loads configuration and code from; its docs list `hooks` and `config` inside `.git` under "In your working directory only"; it covers shell commands only — AUTHORITY (docs, 1 voice)
  > "Inside the directories that sandboxed commands can write to, the sandbox still denies writes to the files Claude Code loads configuration and code from." [10 @ 40000]
  > "**In your working directory only**: shell startup files such as `.bashrc` and `.zshrc`, `.gitconfig`, the `.vscode` and `.idea` directories, and `hooks` and `config` inside `.git`" [10 @ 40000]
  > "The sandbox covers shell commands only." [10]
- Docker Sandboxes: a direct mount is read-write; a mountless sandbox clones inside the sandbox with no host workspace attached; the host repository is available at /run/sandbox/source read-only; a host worktree gives a task its own branch and directory with edits visible on the host; simultaneous tasks get a separate worktree or clone each inside the sandbox; branches alone do not isolate edits — AUTHORITY (Docker docs)
  > "A direct mount is read-write, so the agent edits your working tree in place." [13]
  > "Use a mountless sandbox to clone repositories inside the sandbox without attaching a host workspace." [14]
  > "Your host repository is also available at /run/sandbox/source, but only with read access." [14]
  > "A host worktree gives a task its own branch and directory while keeping edits visible on the host." [14]
  > "For simultaneous tasks, have the agent create a separate worktree or clone for each task inside the sandbox." [14]
  > "Branches alone don't isolate edits in a shared working directory." [14]
- Credentials kept outside the sandbox and reaching the agent only via a host-side proxy, a scoped token, or a placeholder is the converging pattern — CONVERGENCE (6 source URLs: Anthropic web sandbox, Anthropic Cowork, Docker sbx, nanoclaw ×2 files of one project, microsandbox)
  > "We've designed this sandbox to ensure that sensitive credentials (such as git credentials or signing keys) are never inside the sandbox with Claude Code." [25]
  > "The proxy verifies this credential and the contents of the git interaction (e.g. ensuring it is only pushing to the configured branch), then attaches the right authentication token before sending the request to GitHub." [25]
  > "Claude Cowork's answer to agent identity is concrete: credentials stay in the host keychain, the VM gets a per-session scoped-down token, and that token can be revoked independently of the user's." [26 @ 20000]
  > "For example, if credentials never enter the sandbox, they can't be exfiltrated, regardless of whether the cause is a user, a model finding a “creative” path, or an attacker." [26]
  > "Credentials: the host-side proxy injects authentication headers into outbound HTTP requests." [13]
  > "NanoClaw normally runs API calls through an OneCLI HTTPS proxy that injects real credentials in place of a placeholder key." [15]
  > "Note: an agent group's OneCLI agent receives only the secrets attached to it." [16]
  > "So a workload can call an API with a credential it never actually holds." [11]
- microsandbox: substitution needs TLS inspection for that host; the allowed endpoint receives the real credential; per-mount `readonly` / `ro` for a mount the guest should not write — AUTHORITY (docs)
  > "It needs TLS inspection for that host." [11]
  > "The allowed endpoint receives the real credential." [11]
  > "`readonly` / `ro` when the guest should not write to the mount." [12]
- nanoclaw: a `readOnly: false` grant was silently forced read-only; the container runner mounts a session dir at /workspace (readonly false, mountClass group-state) — AUTHORITY (source, 1 voice)
  > "so a `readOnly: false` grant was silently forced read-only." [17]
  > `mounts.push({ hostPath: sessDir, containerPath: '/workspace', readonly: false, mountClass: 'group-state', scope });` [18]
- Git refuses by default to parse the config of a repository owned by someone else, let alone run its hooks; the setting for exceptions is only respected in protected configuration — AUTHORITY (git source, 1 voice)
  > "By default, Git will refuse to even parse a Git config of a repository owned by someone else, let alone run its hooks, and this config setting allows users to specify exceptions, e.g. for intentionally shared repositories (see the `--shared` option in linkgit:git-init[1])." [19]
  > "This config setting is only respected in protected configuration (see <<SCOPES>>)." [19]
- Git can be configured to run another command instead of `ssh` for fetch/push, `core.hooksPath` can disable hooks, and hooks default to `$GIT_DIR/hooks` — AUTHORITY (git source, 1 voice)
  > "If this variable is set, `git fetch` and `git push` will use the specified command instead of `ssh` when they need to connect to a remote system." [22]
  > "You can also disable all hooks entirely by setting `core.hooksPath` to `/dev/null`." [22]
  > "By default Git will look for your hooks in the `$GIT_DIR/hooks` directory." [22]
- git init can create a text file instead of a `.git` directory, holding the path to the actual repository — AUTHORITY (git source, 1 voice)
  > "Instead of initializing the repository as a directory to either `$GIT_DIR` or `./.git/`, create a text file there containing the path to the actual repository." [30]
- Cursor before 2.5: a malicious (e.g. prompt-injected) agent inside the sandbox could rewrite the insufficiently protected .git config, and if it could write Git hooks, code ran outside the sandbox when Git next fired the hook — AUTHORITY (secondary write-up, 1 voice)
  > "In Cursor before 2.5, a malicious agent inside the sandbox — say, one that had been prompt-injected — could rewrite the insufficiently protected .git config." [23]
  > "If it could also write to Git hooks, the next time Git fired that hook, code ran outside the sandbox." [23]
- GitSpawn write-up: git clone, fetch and pull do not copy a remote repository's local .git/config, and a git clone from a stranger is safer than a .zip from a colleague — AUTHORITY (secondary write-up, 1 voice)
  > "git clone, fetch, and pull do not copy a remote repository's local .git/config." [24]
  > "The counterintuitive lesson: a git clone from a stranger is safer here than a .zip from a colleague." [24]
- GitHub token shapes: tokens limitable to specific repositories, fine-grained permissions, installation tokens expiring after 1 hour, `gh auth setup-git` configures git to use GitHub CLI as credential helper — AUTHORITY (GitHub docs, 3 pages)
  > "Each token can be further limited to only access specific repositories for that user or organization." [27]
  > "Each token is granted specific, fine-grained permissions, which offer more control than the scopes granted to personal access tokens (classic)." [27]
  > "The installation access token will expire after 1 hour." [28]
  > "This command configures git to use GitHub CLI as a credential helper." [29]

## Dissent and counter-arguments
- Copilot cloud agent cannot directly run git push or other Git commands, unlike the rip-cage model of the agent running git with an injected token; single vendor.
  > "It cannot directly run git push or other Git commands." [4]
- Codex removes secrets before the agent phase starts, which sits against "secrets reach the agent via runtime injection".
  > "For security reasons, secrets are removed before the agent phase starts." [1]
- Docker's `sbx run` shares a host workspace directory, defaulting to the current directory, so "never bind-mount" is stricter than that tool's default.
  > "Host workspace directory: shared when you pass a workspace path or use sbx run, which defaults to the current directory." [13]
- Claude Code keeps the checkout writable; on Linux or WSL2 with `allowNestedUserNamespaces` true it says not to rely on protected paths.
  > "If you set [`allowNestedUserNamespaces`](https://code.claude.com/docs/en/settings-reference#sandbox-allownestedusernamespaces) to `true` on Linux or WSL2, don't rely on protected paths: code from a sandboxed command can end up running outside the sandbox." [10 @ 40000]
- Claude Code's `.git` hooks/config entry is scoped to the working directory; whether nested repos are covered is not stated (that this is the gap a hide-nested-repos rule would fill is inference).
  > "**In your working directory only**: shell startup files such as `.bashrc` and `.zshrc`, `.gitconfig`, the `.vscode` and `.idea` directories, and `hooks` and `config` inside `.git`" [10 @ 40000]
- Per the GitSpawn write-up, git clone, fetch and pull do not copy a remote's local .git/config, which argues for fresh clones.
  > "git clone, fetch, and pull do not copy a remote repository's local .git/config." [24]
- Anthropic says its custom allowlist proxy was the piece that failed.
  > "Our custom allowlist proxy was the piece that failed." [26 @ 20000]
- microsandbox concedes substitution needs TLS inspection for that host.
  > "It needs TLS inspection for that host." [11]
- Searched, none found: a source recommending bind-mounting host checkouts read-write as hardened practice (query "AI coding agent writes .git/config or .git/hooks sandbox escape host code execution" returned only advisories; one search only). No web search was run for the hosted angle.

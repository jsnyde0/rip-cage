# ADR-032: Host-tool line — a declared, typed call from the cage to a host command

**Status:** Proposed — 2026-11-06, bead `rip-cage-mgp6`; decisions human-ratified in-pane in one brainstorm sitting (rulings recorded as comments on that bead), then two fresh-context adversarial review rounds folded before filing (records on that bead), and further rounds folded by `brain:rip-cage-jdl2` after filing (one record per round on epic `rip-cage-jdl2`; the last fold is unreviewed by a fresh round and is named as such in the hand-up). The code lands under that epic; this ADR is the canon it implements.

**Firmness:** per-decision, see each Dn. D1, D2, D3, D4, D5 FIRM (D2 and D3 each carry a FLEXIBLE vocabulary inside the FIRM rule, stated in the decision); D6, D7 FLEXIBLE.

**Citation form:** `rip-cage ADR-032 D<k>`. Bare `ADR-032` is ambiguous across corpora (see rip-cage ADR-031's citation note).

## Context

msb `--secret` gives a caged agent the use of a credential without possessing it — for exactly one shape of secret: a value msb can substitute into an HTTP header, query or body on a TLS-intercepted flow toward an allowed host (rip-cage ADR-029 D5). A second class exists that it cannot reach: protocols that are not HTTP (Telegram's MTProto, SSH, IMAP/SMTP, database wires), HTTPS where the key *signs* the request instead of being sent (AWS SigV4, HMAC APIs), and tools whose reply would hand a key back (token refresh). For that class the operator of the `switch-desk` project improvised cage-to-host plumbing by hand — a gate on the Docker bridge, a command-shape table, a unix-socket keyholder process, a Telegram approval card — and the human ruled that this plumbing is not a project's job but rip-cage's (`switch-desk` bead `sd-952`, 2026-11-06).

Three research files precede this ADR and are its evidence base: `docs/2026-11-06-host-tool-line-R1-prior-art.md` (rip-cage never had a configured host-tool line; the nearest things — the ADR-026 D5 mediator seam and ssh-agent forwarding — retired when `--secret` made them redundant, and the ssh forward also leaked every host key), `-R2-risks.md` (the must-holds: argv-only exec, verb parameters constrained host-side, no credentials in replies, an authenticated or non-network channel; a host-tool line is a path *around* the egress allowlist), and `-R3-msb-native.md` (msb has had `--vsock HOST_PATH:PORT` since 0.6.9: the guest dials AF_VSOCK CID 2, msb connects it to a host unix socket, no TCP, no LAN, outside the network policy; it is a create-time flag with no `--conf` key; msb has no host-exec or hook surface).

Measured in the sitting (msb 0.7.8, Linux/KVM, scratch sandbox, `rip-cage-mgp6` comments) — five facts: bytes cross under `network.policy: none` with egress still denied; the route survives `msb stop`/`start`; a missing host socket is a fast connect error, never a boot failure, and recovers when the socket reappears; the route is visible at `msb inspect --format json` under `active_config.vsock.routes[]` while the cage runs (`active_config` is null on a stopped cage, and `config` carries no vsock key — verified on 0.7.8); **payloads of 64 KiB and above stall or time out.** Two further facts the design relies on were **not** measured in the sitting and are proven by the epic instead: that a neighbouring port without a route is refused instantly (the `rc test` route sample, epic child .6), and that **a dead gatekeeper behind a live route produces the same fast connect error as no route at all** (the epic's hand-verified live run: the gatekeeper killed by hand on the scratch cage, `host-tool --list` exiting 5 within seconds, plain `rc up` restarting it — the only step that traverses a dead gatekeeper behind a live vsock route). `brain:switch-desk` confirmed (mail, 2026-11-06 16:15) that every keyholder request fits under 32 KiB, three replies need paging, paging is acceptable, and no bulk transfer is planned.

## Terms

- **Host tool** — an operator-owned command on the host that holds, or can reach, a credential the cage must never possess. rip-cage names none.
- **Line** — the whole mechanism this ADR defines: declaration, channel, gatekeeper, in-cage client. One line per cage; many tools and verbs on it.
- **Declaration** — the host-side file listing, per tool, the verbs the cage may call: each verb's fixed command line, its typed slots, its timeout, and whether its reply may carry a credential.
- **Verb** — one named call on one tool, mapped to one fixed host command line.
- **Slot** — a typed hole in a verb's command line that the agent's argument fills after validation.
- **Gatekeeper** — the host-side process rip-cage ships: it listens on the line's unix socket, validates each call against the declaration, runs the command as an argv array, and returns a typed reply. **Every decision the line makes is made here.**
- **`host-tool`** — the in-cage client baked into the base image. It is the shipped convenience door, not a boundary: any guest process could dial the vsock port, and the gatekeeper would treat it identically.
- **State directory** — `${RC_STATE_DIR:-${XDG_STATE_HOME:-$HOME/.local/state}/rip-cage}/<cage>/`, new with this ADR: rc's control plane for the line — the socket, pid file, normalized declaration, log, lock, and the `calls/` tree of call directories. The control files are never a tool's working directory; `rc destroy` removes the whole directory. The path in force is stamped on the cage as the create-time label `rc.state-dir`, so `rc destroy` and `rc doctor` find the same directory `rc up` used whatever `RC_STATE_DIR` is set to later. No cage launched after this ADR can mount it or any directory containing it: it is one of rc's **authority directories** (D2).
- **Call directory** — a fresh, empty, 0700 directory under `<state>/calls/` that the gatekeeper creates for one call, runs the command in as both working directory and `HOME`, and removes when the call ends (D6). Nothing a tool writes *there* outlives its call, so no verb plants a dotfile, a pid file or an answer file for the next one through ambient state. **It is a no-carry-over boundary, not a write barrier:** a declared tool runs as the operator and can write anywhere the operator can, including `../../tools.json`; what keeps the control plane honest is D2 — a tool is operator-declared code resolving outside every mount, the same trust rc itself runs under — plus a slot rule that refuses `..` and `/` in values unless the slot opts in. A tool that needs persistence names a fixed absolute path in its declaration (D4).
- **Authority directory** — a host-side directory whose contents decide what a cage may do: the secrets directory msb `--secret` reads from, the **default projects directory** `${XDG_CONFIG_HOME:-$HOME/.config}/rip-cage/projects` (always, whatever `--conf` points at — it holds every default-lookup cage's declaration), the directory holding this cage's config when `--conf` puts it elsewhere, and the state directory root. A config mount row that is one of them, contains one, or lies inside one is refused; an rc-computed mount that does is dropped with a warning, as every best-effort computed mount already is (D2).

## Decisions

### D1: rip-cage owns the line as a generic seam and names no tool

**Firmness: FIRM** (human-ratified in-pane 2026-11-06, "A" on the own-it-or-not decision; consequence of rip-cage ADR-005 D12)

rc owns the mechanical parts that are identical for every tool: the channel, the declaration schema and its validation, the gatekeeper, the in-cage client, lifecycle, and doctor/test visibility. The tool, its verbs, and anything that wraps a verb (approval, rate limits, allowlists) are operator composition, declared in config and never special-cased in rc. A worked declaration and wrapper live under `examples/`, never in the binary.

**Rationale:** `direct:` R2 §1 and §4 — the dangerous part of a host-tool call is the argument check, not the pipe; if every tool re-implements it, the second tool is the one that forgets. `direct:` the human, in-pane: "it puts the dangerous part in one place, written once." `reasoned:` a generic validator in front of an operator's command is a composition interface in rip-cage ADR-005 D12's sense, the same shape as the retired ADR-026 D5 mediator seam ("rc owns the interface, blesses no mediator, none by default").

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| Channel only: rc provides the vsock route; each tool validates its own verbs and approvals | `reasoned:` leaves R2's must-holds (argv-only, constrained parameters) to every tool author; one sloppy tool is a host hole. `direct:` the human chose A over B after this exact framing. |
| Nothing in rc; the desk keeps its plumbing | `direct:` `sd-952` — the human ruled the plumbing is not the desk's job. |
| A Telegram-specific line | `direct:` rip-cage ADR-005 D12 forbids rc naming a tool. |

**What would invalidate this:** a second operator building their own validator *beside* the gatekeeper because its slot vocabulary cannot express their verb — that is the cue D3's vocabulary is too narrow, not that D1 is wrong.

### D2: The declaration is a host-side sibling file, read by rc and never merged into the msb config

**Firmness: FIRM** (the location rule and the "never merged" rule; the file name and schema below are FLEXIBLE. Human-ratified in-pane 2026-11-06, including the one-sentence amendment to rip-cage ADR-031 D2 this requires)

The declaration lives next to the project config: for the default lookup, `${XDG_CONFIG_HOME:-$HOME/.config}/rip-cage/projects/<cage>.tools.yaml`, in the directory rip-cage ADR-031 D5(a) already reserves for composition inputs; when the config is given by `--conf` or `RC_CAGE_CONF` (`cli/up.sh`, `_up_resolve_conf`), the sibling `<config-stem>.tools.yaml` beside that file's real path (`realpath`, so a relative `--conf ./x.yaml` and the `rc.cage-conf` label doctor reads later name the same absolute file). Either way it is host-side, outside every cage mount (the config file itself is already required to be), never on a path a cage config can point at. rc reads it at `rc up` and refuses to create or start a cage unless every check passes:

- **Authority directories stay unmounted.** The predicate that already refuses a mount source exposing the secrets directory (`_mount_src_exposes_secrets_dir`, `cli/lib/protected_paths.sh`) generalises to rc's authority directories (Terms): a mount source whose real path equals, contains, or lies inside the default projects directory (always), the `--conf` config's directory (when different), or the state directory root. For the `--conf` directory only equals-or-contains applies — a mount strictly inside it cannot expose the config or its sibling declaration, and the common config-beside-project layout must keep working (ruling 2026-11-09, round-9 fold under rip-cage-jdl2.3.1). For a **config row** that is a refusal naming the directory; for a mount **rc computes** (worktree `.git`, skill-symlink parents, the substrate projection) it is warn-and-skip — the computed mount is dropped and the launch proceeds — exactly the posture both existing predicates take at those sites today (`cli/up.sh`, the skill-parent, agent-parent, symlink-follow and pi-substrate sites), because a computed mount is best-effort decoration and a refusal there would brick a cage that has no declaration at all. The state directory root is matched **whether or not it exists** — rc creates it the moment any cage declares a tool, so a mount that would contain it is refused up front; the secrets directory keeps its existing existence rule. The `protected-paths` list is not the mechanism: it matches single path components, and these are directories at a depth it never scans. `RC_STATE_DIR` is honoured by the same check, so pointing it into a workspace is refused like any other overlap. Because the state directory holds the normalized declaration and the pid rc signals, this is the check that keeps a caged agent from rewriting its own verbs or redirecting rc's own stop. **Known residual, accepted:** a cage created before this ADR with `~/.local/state` or a parent of it mounted read-write keeps that mount until its next `rc up`, which refuses it; until then it can see a state directory another cage's first declaration creates. The epic's docs child records it.
- **Every `/`-anchored substring of every `argv` literal resolves outside every mount — a layer, deliberately conservative.** Enumerating path shapes cannot be completed (review rounds 4–8 each found a new one: `--opt=`, `key=`, `-F/path`, `@/path`, `file:///path`), so the rule does not enumerate. For each literal element (not a slot), after splitting at every `=`: a literal that begins with `./` or `~`, or contains a `..` segment, is refused outright; then **every substring that begins at a `/`** (leading slashes collapsed) is a candidate path. Each candidate is resolved component by component: a symlink component is followed, and a component that is a symlink whose target cannot be resolved — a dangling link — refuses, because the cage could create the target; a candidate that does not exist is resolved through its longest existing ancestor plus the remaining suffix. A candidate whose resolution equals or lies inside any mount source refuses the declaration, naming the element. A candidate that resolves nowhere near a mount passes, which is why ordinary literals survive: `refs/heads/main` yields `/heads/main`, `application/json` yields `/json`, a URL yields `/host/v1` — none lies in a mount. **A false refusal is acceptable** (the operator rewrites the element); a missed shape is not. `argv[0]` is a literal, absolute, exists and is executable; a slot never fills `argv[0]`. **What rc checks is the files `argv` names, not the code those files load** — a shebang's interpreter, a venv behind an entry point, a sourced library, a `.pth` in system site-packages: that is the operator's composition, and the honest instruction, repeated by `rc doctor`'s bypass sentence, the reference doc and the `cage-config` skill, is to declare tools whose whole install lives outside every mount. **What this rule cannot declare, held as fog in the epic:** a verb that runs a host tool *over the mounted workspace itself* — `git -C <workspace> push` with the host's keys — because the workspace is a mount and a tool reading guest-writable config or hooks from it is host code execution from the cage. rc already has the mechanism that makes host-side git over a mounted repo safe (`_git_exec_covers`, rip-cage ADR-002 D11: the repo's config and hooks are covered in the guest view); whether that cover is the admission condition for such a verb is a decision for the first project that needs one, not this ADR.
- **Shape.** Placeholders and slots match one-to-one; no unknown keys; tool, verb and slot names match `^[a-z][a-z0-9_-]{0,31}$` (so a name can never read as an option or carry a `/`); timeouts and defaults are typed (D3).

**When the checks run.** The schema and the config-row checks run in `rc up`'s pre-msb floor block, so a defective declaration refuses before any msb call. The check against rc's own computed mounts runs against the **final `msb create` argv as `_up_build_msb_create_argv` assembled it** — every host source in it, from `-v <host>:<guest>` rows and `--mount type=bind,...` rows alike, covers included — immediately before that argv executes, so the list is the one msb will see and no cage is ever created or started against a defective declaration; this is the guarantee, and `--dry-run` shows the refusal. On a cage that already exists (the stopped-cage converge path and the running-cage attach path), the mount set is the one msb recorded at create, read from `msb inspect --format json` (`config.mounts[].host`), and every gatekeeper start on such a cage checks the declaration against that set.

rc merges nothing from the declaration into the msb config; the msb file stays whole and native. With no declaration present there is no route, no socket, no gatekeeper.

Minimal schema (FLEXIBLE; the `cage-config` skill is its documentation home):

```yaml
tools:
  <tool-name>:
    verbs:
      <verb-name>:
        argv: ["/abs/path/to/command", "sub", "--chat", "{chat}", "--limit", "{limit}"]
        slots:
          chat:  {type: string, regex: "^-?[1-9][0-9]*$", allow_dash: true}   # negative ids are legitimate here
          limit: {type: int, min: 1, max: 100, default: 20}
        timeout: 30s            # per verb; a verb that waits on a human declares a long one
        returns_secret: false   # D5
```

**Rationale:** `direct:` rip-cage ADR-031 D5(a) — everything that defines authority lives where the caged agent cannot reach it; R2 §6a names the self-escalation that follows from a declaration in a workspace file, and the same escalation follows from a *script path* inside a mount (`["/usr/bin/python3", "/workspace/tool.py"]`), which is why every path-carrying element is checked, not only the command. `direct:` review round 3 — the protected-paths list matches path components, so a directory entry could never express "this directory and everything containing it"; the secrets-directory predicate is the precedent that does, and the state directory was unchecked altogether though that draft made it every tool's cwd (round 5 then moved tools out of it entirely). `direct:` msb's `--conf` loader is `deny_unknown_fields` (R3 a1, e1), so the declaration cannot live in the msb file. `reasoned:` the protected-paths list is already a second host-side data file rc reads under rip-cage ADR-031 D2; this is the same kind of thing, and it is not a merge: rc never writes it into the msb config, it only acts on it (a launch flag and a host process), which is the carve-out rip-cage ADR-031 D3 already names for `--name`, `--log-level`, computed mounts and covers.

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| Upstream a `vsock:` key to msb's `--conf` and keep everything native | `reasoned:` solves the route only; verbs, slots and timeouts still have no native home. Worth doing later for the route alone (D6 predicate), not a substitute. |
| Smuggle the declaration through a native key (`labels:`, `env:`) | `reasoned:` a schema encoded in label strings is a transpiler in disguise, the thing rip-cage ADR-031 D2 struck. |
| Declare tools in the workspace (`.rip-cage/tools.yaml`) for convenience | `direct:` rip-cage ADR-031 D5(a); R2 §6a — an injected agent would widen its own verbs. |
| Check only `argv[0]` against the mounts | `reasoned:` an interpreter plus a mounted script is host code execution from the workspace; the check is on every path element or it is not a check. |
| Add the projects and state directories to `share/rip-cage/protected-paths` | `direct:` review round 3 — the list matches single path components; `rip-cage/projects` never matches and `projects` would refuse every `~/projects`; the (b) scan stops at depth 2. A predicate is the only shape that says "this directory and every ancestor". |
| Allow `./`, `~` or `..` `argv` elements, resolved against the state directory | `direct:` review round 3 — `../../workspace/x` resolved against the state directory lands in a mount and was never checked; an absolute path names the same file. |
| Treat every literal containing `/` as a path, refusing the rest | `direct:` review round 4 — `refs/heads/main`, `application/json` and `--format=%h/%s` are ordinary tool options; refusing them leaves the operator a slot (agent-controlled) or a shell wrapper (D3's own invalidation cue). Scanning `/`-anchored substrings and refusing only on a mount hit keeps them. |
| Enumerate path shapes (`/`, `./`, `~`, `..`, `--opt=`, `key=`) | `direct:` review round 8 (granter's ruling) — every round found a shape the list missed (`-F/path`, `@/path`, `file:///path`); the list cannot be completed, and D2 is a layer, so a conservative scan with acceptable false refusals replaces it. |
| Chase transitive code loading (shebangs, venvs, `.pth`, sourced libs) | `direct:` review round 8 (granter's ruling) — unbounded, and a wall rip-cage is not building; named as a residual with the one honest instruction instead. |
| A shared host-wide tool library referenced by name | `reasoned:` reuse is real (a keyholder serves several cages) but adds a second file and a resolution rule before any consumer exists; held as fog in the epic. |

**What would invalidate this:** msb ships additive `--conf` layering *and* a native host-tool schema — then the sibling file folds into the msb file through the `cage-config` skill, never through merge code in rc.

### D3: A verb is a fixed command line with typed slots, executed as an argv array, never a shell

**Firmness: FIRM** (the rule; the slot vocabulary and caps below are FLEXIBLE. Human-ratified in-pane 2026-11-06, after the correction that the gatekeeper runs commands, not daemons)

The gatekeeper fills a verb's declared `argv` template from the agent's named arguments, one slot per placeholder, after validating each value against its slot type. It then executes that array directly: **each validated value becomes exactly one argv element**, whatever characters it holds — a value of `; touch x $(id)` reaches the command as that one literal string, never as a shell would read it. No code path joins agent text into a command string; no shell is involved. Validation is strict by construction: regexes are anchored full-matches; every string slot rejects control characters, newlines and NUL; an `int` slot accepts only a JSON integer (never a boolean, never a numeric string) within its declared bounds; an `enum` slot one of its values; values beginning with `-` are rejected unless the slot declares `allow_dash: true`; values containing `/` or a `..` segment are rejected unless the slot declares `allow_slash: true` (a message that quotes a URL opts in; a slot that a tool would read as a file name should not); unknown arguments, missing required slots, unknown verbs and unknown tools are typed errors. **Error messages come from a fixed table keyed by error kind** — plus the slot name for `bad-argument` and the exit status for `tool-failed` — never from an exception's text, so no reply carries a host path, a traceback or an argument value. A positional separator (`--`) is the template author's choice, placed in `argv` where the tool wants it; the gatekeeper does not insert one because the template is fixed and the slots cannot move.

Caps and bounds (FLEXIBLE defaults): the **encoded** request line and the **encoded** reply line are each capped at 32 KiB — the cap is measured on the bytes that cross the vsock, not on the tool's raw stdout, so JSON escaping cannot push a reply past the measured 64 KiB stall; a per-verb timeout; a per-cage concurrency bound, with one slot model (granter's ruling, round 8): **a slot is taken at accept**, held under a short read timeout (10 s to receive the whole request line, after which the connection is closed and the slot freed, so idle connections cannot hold the line `busy`, R2 §1d), and then held for the command's duration — or, for `list`, only for the read: `list` is answered and its slot freed at once. With every slot held by running commands a new connection gets `busy` whether it would list or call; `rc test` therefore retries `list` briefly before calling a saturated line a failure. A command runs in its own session (process group); on timeout the whole group is killed, so a wrapper's grandchildren cannot outlive the call or hold the pipes. A command's exit status and stdout are the whole reply surface: stdout is read with a bound of the cap plus one byte and returned as the result; a request over the cap is `request-too-large` (refused, nothing ran); a reply over the cap is `reply-too-large` (the command **ran**, the group is killed at the bound, nothing partial is returned) — two kinds, because an agent must never retry a side-effecting verb believing it did not run; non-zero exit yields `tool-failed` with **no stderr, path or traceback forwarded** — the command's stderr is the host-side log file itself (never a pipe the gatekeeper must drain, so a chatty tool cannot block), and that log, which may therefore echo arguments, lives in the state directory (R2 §3b).

Initial slot vocabulary (FLEXIBLE): `string` (optional `max` length, default 4096 bytes; optional `regex`, `allow_dash`, `allow_slash`), `int` (`min`, `max`), `enum` (`values`), each with an optional `default` of the slot's own type. There is deliberately **no path-typed slot** in the first cut (R2 §1c); a tool that needs a file takes it through a mount, not an argument. What rc cannot know is how a tool reads a string it is handed: `["/usr/bin/python3", "{script}"]` is host code execution however the slot is typed. The `allow_slash` default closes the obvious shape; the rest is the declaration author's judgment, and the `cage-config` skill names that interpreter shape as the anti-pattern.

Long-lived tools (a Telegram session that must stay logged in) are the operator's business: the declared command is that tool's own small client, and keeping the daemon alive is not rc's job. rc checks at `rc up` that the command exists and is executable, nothing more. The group kill reaches every process still in the command's session; a grandchild that calls `setsid` itself leaves it, which is a known residual of process-group semantics, not something rc chases.

**Rationale:** `direct:` R2 §1a–1b (host RCE from a prompt-injected agent via shell metacharacters or option smuggling; "cheapest mitigation: rc execs an argv array, never a shell"). `direct:` the human, in-pane: ssh signing and git push are plain host commands and must not need a daemon — the exec model serves them; declaring one *over the mounted workspace* is the D2 fog above, not a daemon question. `direct:` the desk's keyholder already exposes exactly such a client (`keyholder-telegram <verb>`), reached by the desk's gate via argv. `reasoned:` one mode (exec) is less surface than two (exec plus socket-forward) and already covers the daemon case through its client. `direct:` review round 1 — the 32 KiB cap on raw stdout would have let a 6× JSON-escaped reply reach the stall; `$`-anchored regexes admit a trailing newline; Python's `bool` is an `int`; `subprocess` kills only its direct child.

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| Forward framed JSON to the tool's own unix socket | `reasoned:` two modes for one job; the daemon case is already served by exec-ing the daemon's client. Held as fog if a tool appears with no CLI. |
| Shell template with quoting | `direct:` R2 §1a; quoting is the bug class, not the fix. |
| Trust the tool to validate its own arguments | `direct:` D1's warrant — the check is the dangerous part and belongs in one place. |
| Gatekeeper inserts `--` before positionals (R2 constraint 1) | `reasoned:` meaningful for free-form argv, not for a fixed template where the author places slots and separators; inserting one blindly breaks tools that take no `--`. |
| A per-session call budget (R2 §4c) | `reasoned:` deferred: timeouts plus the concurrency bound cover the runaway case; a budget needs a reset policy nobody can state yet. Fog in the epic. |

**What would invalidate this:** a legitimate verb that cannot be expressed as fixed argv plus typed slots (streaming input, a path the tool must open itself). The cue is an operator wrapping the gatekeeper in a shell script to get around it — widen the vocabulary then, never relax the no-shell rule.

### D4: rc has no approval concept

**Firmness: FIRM** (human-ratified in-pane 2026-11-06: "I'm not sure rc needs to know about all this stuff; we just want to provide the clean mechanical seam")

Nothing in the declaration, the gatekeeper or the client knows the words approval, hook, card or policy. A verb that should ask before it acts is declared with a wrapper command that asks however the operator likes — show a card and wait, check a recipient allowlist, rate-limit — and then runs the real command or exits non-zero. The only things rc gives that case are D3's per-verb timeout, so a verb that waits on a human declares a long one, and D3's typed "tool failed" reply, so a denied agent carries on with other work instead of hanging. **A wrapper has no terminal:** it runs from the gatekeeper with stdin closed, detached from any session; a recipe that asks must ask through something that is not a prompt on stdin. **A wrapper's own authority rides the same rules as the verb's:** whatever decides what it runs — the asker it calls, its budget, the inbox where it writes a request and waits for an answer — is a fixed absolute path or value in the declaration's `argv`, so D2's outside-every-mount check covers each path, and the `cage-config` skill says such a path is authority to keep unmounted (review rounds 3–5: a wrapper config under `~/.config` was one rw mount away from the agent, and a shared writable directory let one verb plant an answer for the next). Its working directory is the call directory, which does not outlive the call. A worked ask-then-run wrapper is an `examples/` recipe.

**Rationale:** `direct:` the human struck the hook as "bringing in how something else externally works into rc." `reasoned:` an approval protocol is the highest-drift part of the whole design (today a desk card, tomorrow something else); rip-cage ADR-026 D2's drift-rate test puts it outside rc. `reasoned:` nothing is lost on safety: the gatekeeper validates the arguments before the wrapper sees them, and because the wrapper both asks and runs, R2 §2b's approved-versus-executed gap closes by construction. `direct:` CLAUDE.md — approval off by default keeps the autonomous path unblocked.

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| A per-verb `approve:` hook in the declaration, fail-closed on anything but an explicit ALLOW | `direct:` the human struck it; `reasoned:` rc would own an approval protocol it cannot keep aligned with whichever app shows the card. |
| Approval inside the gatekeeper as an allowlist DSL | `reasoned:` a policy language is exactly the content-policy business rip-cage ADR-026 D1 keeps out of rc. |

**What would invalidate this:** several operators independently writing the same ask-then-run wrapper shape — that is a cue for a better `examples/` recipe, and only if the shapes converge byte-for-byte a cue to reconsider a hook.

### D5: Replies never carry a credential unless the verb declares it

**Firmness: FIRM** (human-ratified in-pane 2026-11-06: "of course!"; consequence of rip-cage ADR-029 D5 and ADR-030)

A verb whose reply must hand the cage a real secret (the token-refresh class) sets `returns_secret: true` in the declaration. `rc doctor` lists such verbs as possession-mode for that cage. The preferred shape for refresh is the tool writing the new value to the host-side store msb `--secret` substitutes from, so the guest keeps its placeholder; a verb that returns the secret is the explicit exception. rc never scrubs reply content (it does not read it; rip-cage ADR-026 D1) — the declaration is the only honesty mechanism.

**Rationale:** `direct:` R2 §3a — a returned key defeats non-possession directly and is the class's sharpest conflict with rip-cage ADR-029 D5. `direct:` the desk keyholder already returns no credential on any verb.

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| Scrub replies for secret-shaped strings in the gatekeeper | `direct:` rip-cage ADR-026 D1 — rc never reads application content; `reasoned:` pattern scrubbing is a false floor. |
| Forbid secret-returning verbs outright | `reasoned:` the token-refresh class is one of the three reasons the line exists; a declared, visible exception is honest, a ban pushes it into an undeclared verb. |

**What would invalidate this:** a cage with a `returns_secret` verb that nobody notices in `rc doctor` — the cue that visibility, not the rule, needs work.

### D6: The channel is msb `--vsock`; the parts, their environment, and their lifecycle

**Firmness: FLEXIBLE** (mechanism measured once, Linux/KVM, msb 0.7.8; macOS/HVF unmeasured — see the epic's spike)

- **Route.** When a declaration exists, `rc up` appends `--vsock <state>/host-tool.sock:7700` to the `msb create` argv it already assembles (within rip-cage ADR-031 D3's "what no config file can hold"). The port is the constant `7700`, one constant in each half (rc and the client); the socket path is under the state directory, mode 0600, owned by the operator, and `rc up` refuses with a clear error if that path exceeds the platform's usable unix-socket path length (103 bytes on macOS, 107 on Linux — `sun_path` less its NUL; the limit lives in one place in rc), naming `RC_STATE_DIR` as the override. The route is a create-time shape and depends only on whether a declaration **exists**, so `rc up` stamps a create-time label `rc.host-tools=present|absent` beside the existing `rc.cage-conf-sha` label (rip-cage ADR-028 D1 instance, no minted state file), and beside it `rc.state-dir=<path>` whenever a declaration exists, so later verbs find the same directory and the stopped-cage converge rip-cage ADR-031 D3 already runs recreates the cage when presence changed. **A cage with no `rc.host-tools` label reads as `absent`** — every cage created before this ADR has no route, so a missing label must not converge the way a missing `rc.cage-conf-sha` does (review round 3: the precedent would have recreated every pre-epic cage on its first `rc up`). Declaration **contents** never force a recreate: the gatekeeper reads the file fresh at every start.
- **What takes effect when.** Honest and the same shape as an egress-allowlist edit. On a cage that is **not running** (stopped, or about to be created), `rc up` first stops any gatekeeper still alive for that cage — a stopped cage can have no in-flight call, so nothing is lost — and starts a fresh one from the current declaration before the cage starts; presence applies via the converge, contents via that fresh start. On a **running** cage, `rc up` only attaches; it restarts the gatekeeper only if it is dead, never kills a live one (in-flight calls, including a pending ask-then-run wrapper, finish), prints one line when the file differs from what the gatekeeper loaded — "host-tool declaration changed; takes effect on `rc up --replace`" — and `rc doctor` reports the same drift. **Revocation on a running cage therefore needs `rc up --replace`**, exactly like a tightened allowlist; revocation on a stopped cage takes effect on plain `rc up`, by the restart above (review round 3: without it a stopped-cage edit silently kept the old verbs, because nothing had stopped the old gatekeeper). `--no-reload` with a presence change is refused with a clear error (a route without a gatekeeper, or the reverse, is not a state rc will create).
- **Gatekeeper.** One process per cage, started by `rc up` **after** `msb create` returns success and before init runs, from the current declaration (on a stopped cage, before `msb start`, per the restart rule above). The gatekeeper itself calls `setsid()` at startup (macOS ships no `setsid` binary), writes its own pid file after that, redirects stdio to the log, and so survives the attached terminal's hangup. rc takes a lock only around the start/stop section — never across attach — and **holds it through the launch and the readiness wait**, so two `rc up` on one cage serialize; the lock rides a fixed descriptor number (bash 3.2 has no `{fd}` allocation), and the gatekeeper is launched with that descriptor closed in the child, so it does not inherit the lock. On macOS the lock is a pid-carrying `mkdir` lock treated as stale when its pid is dead. rc waits up to 5 s for the pid file and a listening socket; if the gatekeeper fails to start, `rc up` exits non-zero naming the log, the cage stays as created with no line (the agent gets exit 5), and nothing is served half-configured. A stale socket — its pid file names a dead process, or there is no pid file and nothing accepts on it — is unlinked by rc before launch; the gatekeeper itself refuses to start if the socket path exists (one owner for that act). The gatekeeper is stopped by `rc destroy`, by `rc up --replace`, by the not-running path above, and when `msb create` or init fails before attach — **never** on attach exit, whose status is the user's shell. Stopping means SIGTERM; the gatekeeper then accepts nothing new, gives in-flight commands 5 s, kills every remaining command group, removes their call directories, and exits; rc sends SIGKILL after a further 5 s and removes socket and pid — so no wrapper outlives its cage (R2 §7a). `rc destroy <cage>` removes the whole state directory, and does so even when the cage itself is already gone (stopping the gatekeeper first); `rc doctor <cage>` on a missing cage says so before its not-found exit ("gatekeeper still running for this name; `rc destroy` stops it"). `rc doctor`, `rc test` and `rc destroy` find a cage's declaration and state directory the way `rc up` did: beside the config the cage's `rc.cage-conf` label names, and at the path its `rc.state-dir` label names (falling back to the default only for a cage with no such label). `rc doctor` further reports a dead gatekeeper and declaration drift. No supervisor and no auto-restart.
- **Environment.** The gatekeeper rebuilds its own process environment at startup to **exactly three variables** — `PATH=<platform constant>` (Linux `/usr/bin:/bin`, macOS `/usr/bin:/bin` — no `/usr/local/bin`, which nothing forbids a cage from mounting; a declared command is absolute anyway), `HOME` (the state directory for the gatekeeper's own process, which never reads it), and `LANG` copied from the launch environment (`C.UTF-8` when absent) — an allowlist built from scratch, never a filtered copy — and runs every command with those three variables, `HOME` re-pointed at that call's directory, and the call directory as working directory. It is never `rc up`'s environment, which holds the real values of every `secrets:` entry under that entry's own name (`cli/up.sh`, `_up_prepare_conf_secret_env`). **`HOME` is a fresh empty directory, not the operator's home, because a tool's dotfiles are authority too** (review round 4): `git` reads `core.sshCommand` and `credential.helper` from `~/.gitconfig`, `gh` reads `pager` from `~/.config/gh`, and a cage that mounts those read-write — which no rule forbids, and an editor-config mount makes ordinary — would let an injected agent run host code through a declared verb by a second path. **And it is fresh per call, not shared, because a shared writable `HOME` is the same hole one directory over** (review round 5): a verb whose tool writes a slot-named file could plant `.gitconfig` for the next verb. A tool therefore finds no dotfiles unless the declaration hands it some: a verb that needs the operator's real git identity declares it as a fixed `argv` literal (`-c include.path=/abs/path/gitconfig` — the `=` split makes it a checked path), or its wrapper sets `HOME` or `XDG_CONFIG_HOME` to a fixed, operator-known path — the same shape as `SSH_AUTH_SOCK` below — and the `cage-config` skill says that doing so makes that path authority to keep unmounted. Tool-specific variables are the wrapper's job; a wrapper that needs a per-login value such as `SSH_AUTH_SOCK` sets it from a fixed, operator-known path. This is a floor property: a tool must not be able to read a secret out of its environment, and must not find a planted binary on `PATH`. The proof is an exact-key-set assertion with `HOME` equal to the call directory, plus a planted-dotfile case (one verb writes `.gitconfig` into its `HOME`; the next verb's `HOME` does not contain it), not a denylist check.
- **Host requirement.** Python 3 standard library on the host. The prerequisite check resolves `python3` to an absolute path under rc's own `PATH` (override `RC_PYTHON3`), **requires that resolved path (symlinks followed) to lie outside every mount the cage gets — the same check D2 applies to a declared `argv[0]`, because this is the interpreter rc itself execs on every `rc up` and on a running-cage restart** (review round 6: a `python3` shim under a mounted `~/.local/bin` on the operator's `PATH` would otherwise be host code the cage can rewrite), runs `<abs> -I -c 'import socket, json, subprocess'` on that path, treats failure or a stub (macOS `/usr/bin/python3` without the Command Line Tools) as missing, refuses before any msb call, and launches the gatekeeper with that same absolute path **and `-I`** — the check and the launch can never resolve different interpreters, and isolated mode means no user site-packages, no script-directory import and no `PYTHON*` variable can put code on the host interpreter's path (review round 7: `~/.local/lib/pythonX.Y/site-packages/usercustomize.py` is imported at every start by default, and `~/.local` is mountable). The in-cage client runs under `python3 -I` for the same reason on its side.
- **Client.** `host-tool <tool> <verb> [--<slot> <value>]...` is baked into the base image beside the floor probe and the skills shim, root-owned and not writable, and the floor probe asserts that through its guard-path list (check `guard-file /usr/local/bin/host-tool`). It dials AF_VSOCK CID 2 on port 7700, sends one JSON line, prints the result to stdout, and exits with a typed code: **0** ok; **2** refused, nothing ran (`no-such-tool`, `no-such-verb`, `bad-argument`, `request-too-large`); **3** the command ran and failed or its reply was withheld (`tool-failed`, `reply-too-large`); **4** the gatekeeper answered but could not run it (`timeout`, `busy`, `unavailable` — command vanished or could not be executed); **5** the line did not answer — connect reset, connect timeout, or a `list` reply that is not valid JSON (a `busy` reply to `list` is an answer, exit 4) — with one message naming all three causes (no declaration for this cage; declaration added but the cage not yet recreated; gatekeeper down) and `rc doctor` on this cage as the operator's next step. The client fetches `list` once per invocation, before the call: it carries each verb's declared timeout (the reply timeout) and each slot's type, from which the client encodes the argument — an `int` slot's text becomes a JSON integer when it is one, otherwise it is sent as given and the gatekeeper refuses it. `--<slot>` always takes the next token as its value, so `--chat -100123` is a value, not an option; `--<slot>=<value>` is accepted too. The probe-checked baked file protects the agent from a tampered client misleading it; it is not what keeps the host safe — the gatekeeper is (rip-cage ADR-029 D2: every decision host-side).
- **Wire.** One JSON line per request — `{"v":1,"tool":"…","verb":"…","args":{…}}` — and one per reply — `{"ok":true,"result":"<stdout>"}` or `{"ok":false,"error":{"kind":"…","message":"…"}}` — with the closed error vocabulary `no-such-tool`, `no-such-verb`, `bad-argument`, `request-too-large`, `reply-too-large`, `timeout`, `tool-failed`, `busy`, `unavailable`. One built-in request, `{"v":1,"list":true}` (a separate field, so no tool or verb name is reserved), returns tool names, verb names, each verb's timeout, and each slot's name and type — never an `argv` template, never a host path. Unknown fields are rejected. The tool pages; the line does not stream.
- **Isolation.** The route exposes exactly one host endpoint, the declared socket; everything else the guest cannot reach is msb's property, unchanged by this ADR (egress still denied, measured). Host processes under the operator's uid can reach the socket too, which is no new capability — they can already run the command. **Known residual, accepted — host-side code a cage can influence:** every host binary rc runs lives somewhere, and a cage that mounts that somewhere read-write can rewrite it for the next `rc up`: the gatekeeper and `rc` itself in the checkout `make install` symlinks to (`Makefile`); `rc` and `msb` in `~/.local/bin`; a declared tool's own files, which D2 checks against *this* cage's mounts only, so a second cage of the same operator can mount them. No ADR has recorded this class until now; this ADR names it, the epic's docs child adds it to rip-cage ADR-024 D6 as a **new** residual beside the host-placed-shim one, and the `cage-config` skill's one instruction follows from it: keep `~/.local`, the rc checkout and every declared tool's install out of your mounts. One operator, one trust domain. On the guest side the mirror: `~/.local/bin` precedes `/usr/local/bin` on the agent's `PATH` (`cage/agent/zshrc`), so an agent can shadow the baked client for itself; rc's own checks invoke the client by absolute path, and the floor probe reports a shadowing `host-tool` earlier on that `PATH` — a tampered client misleads only the agent (rip-cage ADR-024 D5), it never reaches the host.

**Rationale:** `direct:` R3 "Cheapest native line" and the sitting's spike (every measurement above). `direct:` R2 §5 — the LAN-IP listener is open to the LAN and source address is useless for identity; vsock has no network. `reasoned:` baking the client follows how rc ships its other guest halves (floor probe, init, skills shim), and rip-cage ADR-008 D6's version-staleness check already covers image-versus-rc drift. `direct:` review rounds 1 and 2 — rc's environment carries the exported secret values; a `PATH` through a mount is a planted binary; an inherited cwd in the workspace turns a relative script path into workspace code on the host; a gatekeeper started before `msb create` is orphaned on a failed boot; attach exit is the user's shell status, not a failure; a running cage is the normal state and the ADR must say what `rc up` does there; a content hash would recreate a cage, with transcript-loss risk, for an edit that only needs a gatekeeper restart.

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| `host.microsandbox.internal` + `allow host:tcp:<port>` (pure config) | `direct:` R3 a2 — unverified on 0.7.x, last rip-cage measurement was a fake-accept; `reasoned:` every loopback listener on that port becomes reachable, and callers are indistinguishable. |
| Host LAN IP (`rip-cage-o7tx`) | `direct:` R2 §5a–5c; `docs/2026-07-10-current-stack-parity-and-lan-exposure.md` B2 never measured. Dominated by vsock for this consumer. |
| Mount the client from the host at `rc up` instead of baking it | `reasoned:` a mount can be omitted by a config; a baked, probe-checked file cannot. |
| A per-call bearer secret on the wire | `reasoned:` unnecessary on a channel only the routed cage can reach; add only if a shared-socket shape ever appears. |
| Hash the declaration's contents into the converge check | `direct:` review round 2 — recreates a cage (transcript-loss risk) for an edit the gatekeeper's fresh start already applies; presence is the only create-time fact. |
| Restart a live gatekeeper on every `rc up` so edits apply to a running cage | `reasoned:` kills in-flight calls including a pending approval wrapper; the honest rule is the same as the allowlist's — `--replace`. |
| Restart the gatekeeper with backoff (R2 §7b) | `reasoned:` a supervisor is lifecycle machinery rc would then own; exit 5 plus a doctor line plus restart-on-`rc up` is the same autonomy outcome with less surface. |
| Inherit `rc up`'s environment into the gatekeeper, filtered | `direct:` review rounds 1–2 — that environment holds the real secret values under arbitrary names; a filter is a denylist and a denylist test cannot catch a denylist guard. |
| Pass the operator's `HOME`, `XDG_CONFIG_HOME` and `XDG_STATE_HOME` through so tools find their config | `direct:` review round 4 — dotfiles under them are authority (`core.sshCommand`, `credential.helper`), reachable through an ordinary rw config mount; explicit paths in the declaration or a wrapper are the honest form. |
| Run every tool in the state directory as cwd and `HOME` | `direct:` review round 5 — a shared writable `HOME` lets one verb plant a dotfile, a pid file or an answer file for the next; rc's control plane and a tool's scratch must not be the same directory. |
| Add `.gitconfig`, `.config/git`, `.config/gh` to the protected-paths list instead | `reasoned:` the list matches single components, so `.config/git` is inexpressible; and it is an open-ended denylist of every tool's dotfile — the same shape the environment rule rejects. |

**What would invalidate this:** the 64 KiB stall turning out to bite ordinary verbs in practice (the cue is operators raising the cap); msb exposing a `vsock` `--conf` key (then the route becomes config and rc stops appending it); or a measured failure on macOS/HVF.

### D7: Visibility — a line is a path around the egress allowlist, and rc says so

**Firmness: FLEXIBLE**

`rc doctor <cage>` lists every declared tool and verb beside `network.allow`, with one fixed sentence: a host tool reaches whatever its command reaches on the host; the egress allowlist does not see it; rc checked the files its `argv` names, not the code they load. Verbs with `returns_secret` are listed as possession-mode. Doctor also reports a dead or orphaned gatekeeper, a declaration whose presence changed since the cage was created (recreate pending), and contents that differ from what the running gatekeeper loaded (`rc up --replace` pending). `rc test <cage>` proves, from inside the cage and **without naming any tool or verb** (rip-cage ADR-005 D12: rc tests the seam, never an example), that `host-tool --list` matches the declaration, that the declared socket answers, that a neighbouring port is refused, that ordinary egress is still denied, and that `host-tool` refuses an undeclared verb with the typed error — and names plainly that this is a sample of the route's scope, not a proof of msb's isolation. On a cage with no route (its `rc.host-tools` label absent — the label, not the file, selects which arm `rc test` runs, because the label is the route the cage actually has), `rc test` proves the other half: `host-tool` exits 5 with the three-cause message. The `list` comparison is against the normalized declaration the running gatekeeper loaded (`tools.json`), not the file on disk, so contents drift is a doctor finding and not a test failure. `rc test` never calls a declared verb (it cannot know which has side effects) and never stops a live gatekeeper (review round 3: that would kill an operator's in-flight call); the live calls that prove a tool runs in a fresh call directory with the exact environment are the `examples/host-tool` recipe's own test, run with the shipped client against the real gatekeeper host-side, and the epic's hand-verified live run. rip-cage ADR-024 D2's layer table gains a row for the host-mediated path (an epic child edits it in place).

**Rationale:** `direct:` R2 §4b and §11 — the allowlist stops being a sufficient exfiltration layer for any cage that has a line, and the honest move is to say that next to the allowlist, where the operator already looks.

**Alternatives considered:**

| Alternative | Rejection |
|---|---|
| Treat the line as covered by the existing egress story | `direct:` R2 §4b — default-deny egress never sees this traffic. |

**What would invalidate this:** an operator surprised that a verb sent data out despite a tight `network.allow` — the cue that the doctor line was not loud enough.

## What would invalidate this ADR

The line retires, in place, if msb ships a native way for a guest to trigger a declared host command with argument checking, or a `--conf` schema that makes the vsock route plus a verb table native. Partial fire: a native `vsock` key retires only D6's route-appending; the declaration, gatekeeper and client stay until the verb table is native too.

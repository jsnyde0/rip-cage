# R3: what msb natively offers for a cage-to-host tool line, versus what rip-cage would build

Bead: `rip-cage-mgp6` (research R3). Question: what does microsandbox (msb) give a guest for reaching a host-side tool, and what would rip-cage have to build on top?

Method: read-only. Sources, in order: the installed binary (`msb 0.7.8`, from `msb --version`; `msb run|create|exec|ssh|modify --help`), the rip-cage reference docs and template, then upstream `superradcompany/microsandbox` at tag `v0.7.13` (docs, source, release notes, PRs and issues, via `gh api`). No cage was booted and no msb state changed. Upstream paths below are at `v0.7.13` unless a different tag is given.

Version context: rip-cage's floor is `RC_MSB_MIN_VERSION="0.7.4"` (`cli/lib/msb_runtime.sh:58`). This host runs 0.7.8. The latest release is v0.7.13 (2026-11-01).

## Verified vs unverified

**Read directly (CLI output, source or upstream docs):**
- `--vsock` exists on the installed 0.7.8 (`msb run --help`). Its semantics come from upstream docs and the #1297 PR body. The CLI parser is in source. It is absent from the YAML loader (source, `deny_unknown_fields`).
- The gateway→host-loopback rewrite in source at v0.6.4 and v0.7.13, the `host` policy group, and the docs saying the default policy blocks it.
- `--proxy` semantics (docs), and its absence from the YAML network input (source).
- Secret substitution locations, body limits, HTTP/2 body block, trailers excluded, header-field scoping, `passthrough`, identity checks (docs plus PR bodies). The #1354 thread and its closure.
- No hook, callback or plugin surface (CLI help, release notes 0.6.6→0.7.13).

**Measured earlier by rip-cage (on 0.6.4, not re-run):** LAN-IP guest→host TCP works. `host.microsandbox.internal` fake-accepted on macOS. vsock was absent then.

**Inferred, not verified:**
- That a2 now delivers real bytes on 0.7.x (source says yes; the last rip-cage measurement said no). **This needs the two-port spike before any design leans on it.**
- That `network.allow: ["host:tcp:<port>"]` parses as the `host` group in the YAML string form (CLI grammar says groups are valid targets).
- That a vsock route works under rip-cage's `policy: none` (by construction it bypasses IP networking, per #1297, but this was not run). That a missing host socket path fails the connect rather than the boot. What guest tooling the base image needs (`socat` with VSOCK support, or a small client).
- That the c1 upstream proxy sees only re-encrypted TLS (read from a code comment, not traced).
- d2 (binding a secret to the host gateway over plain HTTP).
- d3's effect on rip-cage's no-verbatim-placeholder rule on ≥0.7.5.
- That ingress to a published port under `policy: none` needs an explicit ingress rule.

## Cheapest native line

**`--vsock HOST_PATH:PORT` (msb ≥0.6.9, inside the 0.7.4 floor).** A host Unix socket becomes a guest-reachable stream on AF_VSOCK CID 2. It needs no TCP port, no LAN or loopback listener, and no egress rule, and it never touches the TLS proxy or the secret machinery. A Unix-socket service also gets host-side access control for free (file mode on the socket path), and only cages launched with that route can reach it. Other loopback processes cannot, which is the opposite of a2. What msb does not give: a YAML key (rc must append the flag at launch, `cli/up.sh:1582`), any request semantics (verbs, approval, the tool itself), and a guest-side client (a socat-style VSOCK→UNIX shim in the image). It is one-directional in initiation (guest dials host). For the host to call in, use `-p` publish (a4) or `msb exec` (a5).

Runner-up: `host.microsandbox.internal` plus `allow host:tcp:<port>` (a2). This is pure config with no rc flag, and the host tool binds loopback. It is not verified on 0.7.x, and every loopback listener on that port becomes reachable.
